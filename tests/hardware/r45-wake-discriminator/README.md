# R45 sole-owner wake discriminator

This directory contains the **diagnostic apparatus** for Foreman packet
`A001-HW1-SOLE-OWNER-WAKE-DISCRIMINATOR-R45`.

It does not replace PS-to-VNC product behavior, does not qualify hardware, and
must not be executed on the PS2 by Reconstruction. Reconstruction owns only the
source/build/host validation of this apparatus.

## Question answered later by hardware

The later hardware role must answer one narrow question on the exact pinned
PS2SDK environment:

> After the sole physical I/O owner has missed outbound-ready and entered its
> 1000-us physical readiness call, can another EE thread publish outbound work
> and receive real serialization completion without any future inbound
> application data?

The two variants are intentionally identical except for that disputed readiness
schedule.

| Variant | Compile define | Readiness | Post-probe second PollSema |
| --- | --- | ---: | --- |
| baseline | `R45_ZERO_TIMEOUT_CONTROL=0` | 1000 us | no |
| control | `R45_ZERO_TIMEOUT_CONTROL=1` | 0 us | yes |

The baseline is the independently validated/HW1-failed pre-R44 product
scheduling shape. The control is the unaccepted R44 candidate scheduling shape.
Neither variant is itself product source.

## PS2 harness contract

`r45_wake_discriminator.c` uses:

- the pinned PS2SDK networking stack;
- the repository's ordinary PS2 network initialization seam;
- one TCP connection from PS2 `192.168.50.2` to Pi `192.168.50.1:5961`;
- one EE owner thread that alone calls socket `select()` and `send()`;
- one EE submitter thread that never accesses the socket;
- a real `PollSema` outbound-ready rendezvous;
- 4096 consecutive isolated publication cycles.

For every cycle the owner first proves an outbound-ready miss, releases the
submitter at that exact boundary, then enters the variant's readiness phase.
The submitter publishes cycle N through the owner semaphore and waits for the
owner's actual serialized-send completion. Elapsed time, retry count and local
yield count are never completion authority.

Each successfully serialized cycle sends one 24-byte big-endian record:

| Bytes | Meaning |
| --- | --- |
| 0..3 | ASCII `R45W` |
| 4 | record version 1 |
| 5 | variant: 1 baseline, 2 control |
| 6 | kind 1 = completion |
| 7 | reserved zero |
| 8..11 | cycle |
| 12..15 | sequence |
| 16..19 | readiness timeout in microseconds |
| 20..23 | deterministic checksum |

Cycle and sequence must both be exactly 1..4096 with no gaps or duplicates.

If the PS2 socket becomes readable during measurement, the harness classifies
the apparatus invalid rather than consuming the peer data as a wake. This keeps
future inbound traffic out of the disputed progress mechanism.

## Pi recorder contract

`r45_wake_recorder.py` accepts and records the PS2 completion records. It has
**no application send/sendall/sendto call**. TCP acknowledgements generated by
the network stack are not application wake traffic.

Example later-hardware invocation for the baseline:

```sh
python3 tests/hardware/r45-wake-discriminator/r45_wake_recorder.py \
    --variant baseline \
    --records /tmp/r45-baseline.jsonl \
    --summary /tmp/r45-baseline-summary.json
```

For the control, replace `baseline` with `control`.

A recorder idle timeout may classify a hardware run as STALL, but never as PASS.
PASS requires all 4096 exact owner-serialized completion records.

Host-only apparatus regressions:

```sh
python3 tests/hardware/r45-wake-discriminator/r45_wake_recorder_test.py
python3 tests/hardware/r45-wake-discriminator/r45_wake_discriminator_source_test.py
```

The recorder regression covers baseline/control record validation, monotonic
sequence, STALL classification, malformed-order rejection and the
no-application-send source invariant. The harness source regression proves the
single socket-send site, single select site, no receive path, no socket access
from the submitter, exact variant constants and the intentional publication
priority relationship.

## Deterministic build

Build both variants twice using the exact pinned toolchain:

```sh
bash tests/hardware/r45-wake-discriminator/build.sh
```

The builder:

- verifies the qualified frozen PS2IP archive identity;
- uses
  `ps2dev/ps2dev@sha256:8fba50ecc2229acd7f8da63d34302f12939b7d4fa6848dda1e6a0ce083321a11`;
- builds baseline twice and requires byte equality;
- builds control twice and requires byte equality;
- requires distinct baseline/control ELF and PT_LOAD identities;
- checks the embedded variant identity string;
- records exact hashes in
  `build/r45-wake-discriminator/BUILD-AUTHORITY.env`;
- never deploys or launches an ELF.

Canonical output files are:

- `build/r45-wake-discriminator/R45-WAKE-BASELINE-1000US.ELF`;
- `build/r45-wake-discriminator/R45-WAKE-CONTROL-ZERO.ELF`.

## Later hardware classification

R45 Reconstruction does **not** choose among these outcomes. A later authorized
hardware role must preserve evidence and classify the focused experiment as
exactly one of:

- `BASELINE_STALLS_CONTROL_PASSES`;
- `BASELINE_PASSES_CONTROL_PASSES`;
- `BASELINE_STALLS_CONTROL_STALLS`;
- `APPARATUS_INVALID`.

Only `BASELINE_STALLS_CONTROL_PASSES` materially supports returning to the R44
zero-timeout candidate for Foreman/Validation redisposition. None of these
categories is product hardware qualification.

## Safety and ownership boundaries

This apparatus does not:

- change PSTV Wire protocol/version;
- use the product RFB provider;
- alter selected RFB queue/credit values;
- add a second physical socket writer;
- add auto-reconnect, watchdog or timeout-success logic;
- diagnose MPEG or AUDIO;
- mutate H1 forensic evidence;
- authorize PS2 execution during Reconstruction.
